# WorkFlow — 중소기업 업무·영업 관리 시스템

업무 배정부터 거래처 상담, 영업 파이프라인, 매출 통계까지 한 곳에서 관리하는 사내 업무관리 시스템입니다.
단순 CRUD가 아니라 **역할 기반 권한(RBAC), 데이터 접근 범위 제어, 감사 로그, 알림** 같은 실무 요구사항을 함께 설계했습니다.

```
┌─────────────────────────────────────────────────────────┐
│ WorkFlow                          🔔 3   정하늘 ▾       │
├───────────┬─────────────────────────────────────────────┤
│ 대시보드  │  오늘 마감    진행 중    이번 달 완료   신규 거래처 │
│ 업무관리  │     6건        24건         87건          8곳   │
│ 업무보드  │                                             │
│ 거래처    │  [ 주간 업무 추이 ]      [ 상태 분포 ]        │
│ 영업관리  │                                             │
│ 매출통계  │  [ 최근 업무 ]           [ 마감 임박 영업건 ]  │
│ 직원관리  │                                             │
└───────────┴─────────────────────────────────────────────┘
```

## 1. 빠른 시작

**사전 요구사항:** Node.js 20+, Docker Desktop

```bash
# 1) 의존성 설치
npm install

# 2) 환경변수 준비 (.env.example 복사 후 AUTH_SECRET 입력)
cp .env.example .env

# 3) PostgreSQL 기동 + 마이그레이션 + Prisma Client + 데모 시드
npm run setup

# 4) 개발 서버 실행 → http://localhost:3000
npm run dev
```

`setup`은 Docker로 PostgreSQL을 띄운 뒤 스키마를 적용하고 시드 데이터를 넣습니다.

`.env` 값은 다음과 같습니다.

| 키 | 설명 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL 연결 문자열. 기본값 `postgresql://workflow:workflow@127.0.0.1:55432/workflow?schema=public` |
| `AUTH_SECRET` | 세션 JWT 서명 키. 임의의 긴 문자열을 넣습니다. |

> 호스트 포트는 **55432**입니다. 로컬에 이미 PostgreSQL(5432/5433)이 떠 있어도 충돌하지 않습니다.

### 데모 계정

시드 데이터로 15명의 직원이 생성됩니다. 비밀번호는 모두 `workflow123` 입니다.

| 역할 | 계정 | 이름 / 직책 | 확인 포인트 |
| --- | --- | --- | --- |
| 관리자 | `admin@workflow.co.kr` | 정하늘 · 경영지원실장 | 모든 메뉴 + 권한 매트릭스 · 활동 로그 |
| 팀장 | `manager.sales@workflow.co.kr` | 김도현 · 영업1팀장 | 전체 업무/영업건 조회, 매출 통계 |
| 영업 | `sales1@workflow.co.kr` | 박지민 · 대리 | 자기 영업건만 보이는 접근 범위 제어 |
| 직원 | `staff1@workflow.co.kr` | 윤재호 · 주임 | 업무 메뉴만 노출, 영업 메뉴 숨김 |

가입 승인 흐름을 확인하려면 `pending1@workflow.co.kr`(승인 대기), 정지 계정 처리는 `suspended1@workflow.co.kr`을 참고하세요.
승인 대기 계정으로 로그인하면 접근이 차단되고, 관리자 화면에서 승인해야 사용할 수 있습니다.

## 2. 기술 스택

| 영역 | 선택 | 이유 |

## 3. 주요 기능

### 대시보드

- 역할에 따라 지표가 달라집니다. 직원은 자기 업무 기준, 팀장·관리자는 전사 기준으로 집계됩니다.
- 시간대별 인사말과 빠른 액션(업무 등록·오늘 마감·칸반·거래처·파이프라인)
- 오늘 마감·지연·진행 중·이번 달 완료 업무, 신규 거래처, 이번 달 수주 금액 KPI
- 주간 업무 추이(라인), 업무 상태 분포(도넛), 월별 매출(바) 차트
- 최근 업무, 마감 임박·정체된 영업건, 다음 액션이 필요한 상담 기록

### 전역 검색 (⌘K)

- 탑바 검색창 또는 `Ctrl/⌘ + K` 로 커맨드 팔레트를 엽니다.
- 업무·거래처·영업건을 코드·제목으로 검색하고, 권한이 있는 메뉴로 바로 이동합니다.
- 조회 범위(스코프)를 그대로 적용해 권한 밖의 데이터가 결과에 나오지 않습니다.

### 업무관리

- **등록 · 수정 · 삭제**: 제목, 설명, 분류, 우선순위, 진행률, 예상/실제 공수, 거래처·영업건 연결
- **담당자 지정**: `task:assign` 권한이 있는 사용자만 다른 사람에게 배정할 수 있고, 배정 즉시 알림이 발송됩니다.
- **마감일 관리**: 마감 임박·지연 업무를 목록과 대시보드에서 별도로 강조합니다.
- **검색 / 필터**: 키워드(디바운스 400ms), 상태, 우선순위, 분류, 담당자, 거래처, 마감 기간 조건을 URL 쿼리로 관리해 새로고침·뒤로가기·링크 공유가 모두 동작합니다.
- **칸반 보드**: HTML5 드래그앤드롭으로 상태를 변경합니다. `useOptimistic`으로 카드가 즉시 이동하고, 서버 실패 시 원래 칸으로 되돌아가며 오류를 표시합니다.
- **댓글 · 첨부파일**: 파일은 `public/` 밖에 저장하고 `/api/attachments/[id]` 라우트에서 권한을 검사한 뒤 스트리밍합니다. URL만 알아도 남의 파일을 받을 수 없습니다.
- **변경 이력**: 어떤 필드가 무엇에서 무엇으로 바뀌었는지 상세 화면에서 확인할 수 있습니다.

### 거래처관리

- 거래처 등록·수정, 등급(A~D)·규모·거래 상태 관리, 담당 영업사원 배정
- **담당자(Contact) 관리**: 거래처별 다중 담당자, 대표 담당자 지정
- **상담 기록**: 유형(전화·방문·이메일·미팅·온라인), 결과(긍정·중립·부정), 다음 액션과 예정일 기록. 영업건과 연결하면 해당 영업건 상세에서도 함께 보입니다.
- 거래처 상세에서 연결된 업무·영업건·상담 이력을 탭으로 확인

### 영업관리

- **파이프라인 보드**: 리드 → 검증 → 제안 → 협상 → 수주/실패 6단계를 드래그앤드롭으로 이동. 단계별 기본 확률이 자동 반영되고, 실패로 옮기면 실패 사유 입력 모달이 뜹니다.
- **목록 뷰**: 단계·계약 상태·담당자·거래처·마감 기간(이번 달/이번 분기/기한 초과) 필터와 정렬
- **계약 상태 관리**: 없음 → 작성 중 → 검토 → 체결/취소, 계약 시작·종료일
- **영업 진행률**: 단계 확률 × 금액으로 가중 예상 매출을 계산합니다.
- **매출 통계**: 월별 매출 추이, 단계별 파이프라인 퍼널, 담당자 랭킹, 상위 거래처, 계약 상태 분포, 실패 사유 분석, 수주율·평균 계약 규모
- **영업 목표**: 담당자별 월 목표 금액을 입력하고 실적 대비 달성률을 표로 확인

### 시스템 관리

- **회원 · 직원 관리**: 등록, 정보 수정, 가입 승인, 정지·복구·퇴사 처리, 삭제(소프트 삭제). 진행 중 업무나 담당 영업건이 남아 있으면 경고를 띄웁니다.
- **부서 관리**: 부서 생성·수정·삭제, 소속 인원과 연간 수주액 확인. 인원이 남아 있으면 삭제를 막습니다.
- **권한 관리**: 역할 × 권한 매트릭스를 체크박스로 편집합니다. 기본 정책과 달라진 항목을 표시하고, 관리자가 자신의 권한을 잠가버리는 것을 방지합니다.
- **활동 로그**: 생성·수정·삭제·로그인·상태 변경·권한 변경·접근 거부를 기록합니다. 사용자·액션·대상·기간으로 필터링하고, 변경 내역은 "이전 → 이후" 형태로 펼쳐 볼 수 있습니다.

## 4. 설계에서 신경 쓴 부분

### 4-1. 역할이 아니라 권한으로 판정한다

`if (role === 'ADMIN')` 처럼 역할을 직접 비교하면 조직 정책이 바뀔 때마다 코드를 고쳐야 합니다.
그래서 **역할 → 권한 → 기능** 3단 구조로 분리하고, 판정은 항상 권한 키로만 합니다.

```ts
// src/lib/permissions.ts — 권한 카탈로그(코드)
export const PERMISSION_GROUPS = [
  { key: 'task', label: '업무관리', permissions: [
    { key: 'task:read:own', label: '내 업무 조회' },
    { key: 'task:read:all', label: '전체 업무 조회' },
    /* ... */
  ]},
  /* ... */
];
```

역할별 허용 여부는 `RolePermission` 테이블에 저장되므로 관리자가 `/admin/permissions`에서 바로 바꿀 수 있고,
새 역할이 추가되어도 검증 로직은 손댈 필요가 없습니다.

가드는 용도별로 나눠 두었습니다.

| 함수 | 용도 |
| --- | --- |
| `requirePermission(key)` | 페이지 진입 가드. 실패 시 `/forbidden`으로 리다이렉트 |
| `requireAnyPermission(...keys)` | "내 것만" / "전체" 처럼 범위만 다른 권한을 함께 허용 |
| `assertPermission(key)` | 서버 액션용. 리다이렉트 대신 예외를 던져 폼 에러로 표시 |

### 4-2. 메뉴를 숨기는 것과 데이터를 막는 것은 다르다

사이드바는 권한에 따라 항목을 숨기지만, 그것만으로는 URL 직접 입력을 막을 수 없습니다.
그래서 **모든 페이지의 서버 컴포넌트와 모든 서버 액션에서 권한을 다시 확인**하고,
쿼리 단계에서도 접근 범위를 좁힙니다.

```ts
// src/lib/scope.ts — 조회 범위를 where 절로 변환
export function taskScopeWhere(scope: AccessScope): Prisma.TaskWhereInput {
  if (scope.canReadAllTasks) return {};
  // 전체 조회 권한이 없으면 내가 담당·요청·관찰하는 업무만 보인다
  return {
    OR: [
      { assigneeId: scope.userId },
      { reporterId: scope.userId },
      { watchers: { some: { userId: scope.userId } } },
    ],
  };
}
```

권한 없는 접근 시도는 차단만 하지 않고 `ACCESS_DENIED` 로그로 남겨 관리자가 확인할 수 있게 했습니다.

`npm run smoke`는 관리자·팀장·영업·직원 네 역할로 세션을 만들어
"보여야 하는 화면은 200, 막혀야 하는 화면은 `/forbidden`으로 리다이렉트" 되는지 한 번에 확인합니다.

### 4-3. 수정 권한과 조회 범위를 함께 본다

`deal:update` 권한이 있어도 자기 조회 범위를 벗어난 남의 영업건은 건드릴 수 없어야 합니다.
두 조건을 한 곳에 모아 판정 누락을 막았습니다.

```ts
export function canEditDeal(scope: AccessScope, deal: { ownerId: string }): boolean {
  if (!scope.permissions.has('deal:update')) return false;
  return canViewDeal(scope, deal);
}
```

### 4-4. 필터 상태를 URL에 둔다

목록 화면의 필터·정렬·페이지는 전부 URL 쿼리에 담습니다. 새로고침해도 조건이 유지되고, 링크로 공유할 수 있고, 뒤로가기가 자연스럽게 동작합니다.
키워드 입력은 400ms 디바운스로 요청 수를 줄이고, 뒤로가기로 URL이 바뀌면 렌더 중 상태를 조정해 입력창을 다시 맞춥니다.

### 4-5. 낙관적 업데이트로 체감 속도를 확보한다

칸반 보드와 파이프라인 보드는 `useOptimistic`으로 드롭 즉시 카드를 옮기고, 서버 액션 결과를 기다립니다.
실패하면 원래 위치로 되돌리고 사유를 보여줍니다.

### 4-6. 감사 로그는 스냅샷 비교로 남긴다

무엇이 바뀌었는지 알 수 없는 "수정됨" 로그는 쓸모가 없습니다.
변경 전후 값을 비교해 실제로 달라진 필드만 골라 저장하고, 화면에서는 한글 필드명으로 "이전 → 이후"를 보여줍니다.

### 4-7. 첨부파일은 공개 디렉터리에 두지 않는다

`public/`에 저장하면 URL을 아는 누구나 내려받을 수 있습니다.
업로드 파일은 프로젝트 외부 경로에 무작위 이름으로 저장하고, `/api/attachments/[id]`에서 세션과 업무 접근 범위를 검사한 뒤에만 스트리밍합니다.

### 4-8. 삭제는 소프트 삭제로 처리한다

직원·거래처·업무·영업건은 `deletedAt`을 채우는 방식으로 삭제합니다.
연결된 이력과 통계가 깨지지 않고, 실수한 삭제를 되돌릴 수 있습니다.

## 5. 프로젝트 구조

```
src/
├─ app/
│  ├─ (auth)/              로그인 · 회원가입 (미인증 레이아웃)
│  ├─ (app)/               인증 필요 화면 (사이드바 셸)
│  │  ├─ dashboard/
│  │  ├─ tasks/            목록 · 보드 · 상세
│  │  ├─ clients/          목록 · 상세(담당자 · 상담 · 업무 · 영업건)
│  │  ├─ sales/            파이프라인 · 상세 · reports(매출 통계)
│  │  ├─ admin/            users · departments · permissions · logs
│  │  └─ forbidden/        권한 부족 안내
│  └─ api/attachments/[id] 권한 검사 후 파일 스트리밍
│
├─ actions/                서버 액션 (auth · tasks · clients · deals · admin · notifications)
├─ data/                   서버 전용 조회 계층 (dashboard · tasks · clients · deals · admin)
├─ lib/
│  ├─ permissions.ts       권한 카탈로그 · 역할별 기본 정책
```

## 6. 스크립트

| 명령 | 설명 |
| --- | --- |
| `npm run dev` | 개발 서버 (webpack) |
| `npm run build` / `npm start` | 프로덕션 빌드 · 실행 |
| `npm run typecheck` | `tsc --noEmit` 타입 검사 |
| `npm run lint` | ESLint |
| `npm run smoke` | 개발 서버 실행 중에 역할별 화면 접근 권한 점검 |
| `npm run setup` | Docker DB 기동 + 마이그레이션 + Prisma Client + 시드 (최초 1회) |
| `npm run db:up` / `db:down` | PostgreSQL 컨테이너 시작 · 중지 |
| `npm run db:migrate` | 개발용 마이그레이션 생성·적용 |
| `npm run db:seed` | 데모 데이터 재생성 |
| `npm run db:reset` | DB 초기화 후 재시드 |
| `npm run db:studio` | Prisma Studio (테이블 GUI) |
| `npm run db:count` | 주요 테이블 레코드 수 확인 |

> **exFAT/FAT 볼륨에서 실행하는 경우**
> `dev` · `build`는 webpack을 사용합니다. Turbopack이 정션 포인트를 만들지 못해 실패하기 때문입니다.
> 또 이 파일시스템은 일반 파일에 `readlink`를 호출하면 `EINVAL` 대신 `EISDIR`를 반환하는데,
> Next의 빌드 트레이싱이 이 코드를 처리하지 못해 프로덕션 빌드가 중단됩니다.
> `next.config.ts`에서 오류 코드를 표준값으로 바꿔 우회하고 있으며, NTFS에서는 아무 영향이 없습니다.
> NTFS 환경이라면 `npm run dev:turbo` · `npm run build:turbo`로 Turbopack을 쓸 수 있습니다.
